Date: 2026-09-04. Answers the checklist in `docs/plans/2026-09-04-zs-implementation-plan.md` § T7
and the BLOCK, WARN and NIT findings of the three Sol audit rounds. Every `file:line` below was

**1 · Server classes and the environment each receives.**
Decision: two classes — `stdio` (command, args, `env` block) and `http` (Streamable HTTP URL, no `env`). A stdio server's child environment is built from empty and receives exactly one enumerated list plus its own approved `env` values: `PATH`, `HOME` (`USERPROFILE` and `SystemRoot` on Windows), `TMPDIR` (`TEMP` and `TMP` on Windows), `LANG`, `LC_ALL`, `TERM`, `SSL_CERT_FILE` and `SSL_CERT_DIR`. The approved values win on a name clash. The eight proxy spellings (`crates/buzz-agent/src/mcp.rs:69-76`) are not on that list: a proxy variable passes only when its value carries no userinfo, and a value carrying credentials is dropped unless the operator has approved it for that one server. The credential handles and command overrides in buzz-agent's own list — `SSH_AUTH_SOCK`, `SSH_AGENT_PID`, `GIT_ASKPASS`, `GIT_SSH_COMMAND`, `GIT_CONFIG_GLOBAL`, `XDG_CONFIG_HOME` — are deliberately excluded, and a registry command must be an absolute path: the `PATH` above is for the child's own subprocesses, never for resolving the command. An http upstream gets no environment; its credential travels as a request header injected at call time. Test: `HTTPS_PROXY=http://employee:token@proxy.example` is treated as a sentinel secret and appears in no unapproved server's environment.
Reason: the ACP wire carries the stdio shape alone (`crates/buzz-acp/src/acp.rs:40`, `crates/buzz-agent/src/types.rs:537`), and an http upstream has no child process to hand variables to. buzz-agent's `PASSTHROUGH_ENV` (`crates/buzz-agent/src/mcp.rs:39-97`) is not a trust boundary to copy: it is applied to untrusted children too and withholds only the four Buzz identity names (`crates/buzz-agent/src/mcp.rs:798-822`), so passing it whole under the word "essentials" would contradict "nothing else" — and an authenticated proxy URL is the one entry on it that is itself a credential.

**2 · Runtime capability matrix.**
Decision: buzz-agent — stdio only; an http entry is rejected under decision 7's semantics, never silently dropped. Claude and Codex — stdio and http, http reached through the proxy of decision 4, both subject to the availability rule in decision 9.
Reason: `McpServerStdio` is the only server variant buzz-agent deserializes (`crates/buzz-agent/src/types.rs:537`). Claude and Codex read native config files; today the bridge only reads them (`desktop/src-tauri/src/managed_agents/config_bridge/claude.rs:14` is `read_config_file`, `codex.rs:125` is `codex_config_path`, and the module has no `fs::write` path at all), so writing those files is this ticket's new work, not existing behaviour.

**3 · Process boundary for stdio servers under Claude and Codex.**
Decision: every generated stdio entry names a bundled launcher, `buzz-mcp-launch`, as its command. The launcher clears the inherited environment, adds only decision 1's list and the server's approved values, strips decision 5's capability variable, and then stays resident as a supervisor rather than `exec`ing. On Linux, wherever cgroup v2 is available and the launcher can create a leaf, it places the server in a dedicated leaf cgroup and kills the whole tree through `cgroup.kill`, which no `setsid()` can leave. Where cgroups are unavailable, and on macOS, the guarantee is weaker and this memo claims no more than it is: the server gets its own process group (`setsid`, or `setpgid` in the pre-exec hook), the launcher relays stdio in both directions and `killpg`s that group on parent death — `prctl(PR_SET_PDEATHSIG)` on Linux, a `kqueue` `EVFILT_PROC` watch or EOF on an inherited parent pipe on macOS — and on its own stdin EOF; but a server that double-forks and calls `setsid()` enters a new session, leaves that group, and survives on macOS (risk below). On Windows the launcher assigns **itself** to a Job Object configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` before it spawns anything, and holds the job handle to process exit; the kernel then places every process the launcher creates in that same job, so the whole tree dies when the handle closes and there is no window in which a server runs outside the job. Every one of `CreateJobObjectW`, `SetInformationJobObject` and `AssignProcessToJobObject` is checked, and any failure exits non-zero before a server is spawned at all. **This supersedes the original `CREATE_SUSPENDED`, assign, `ResumeThread` shape** (amended 2026-09-05, T7b): the post-spawn assignment needs a handle to the child's main thread, which neither `std::process` nor `tokio::process` exposes, so reaching it would mean re-implementing `CreateProcessW` in the launcher; assigning the parent first gives the same guarantee — no server executes outside the job — with the containment established before, rather than around, the spawn.
Reason: the adapter is spawned with no `env_clear` and inherits the harness environment including provider keys and user-defined values (`crates/buzz-acp/src/acp.rs:478`, `desktop/src-tauri/src/managed_agents/runtime.rs:693-695`), so any MCP child it spawns inherits them too. `exec` alone preserves one PID and reaps nothing: a server that forks a daemon outlives the killed adapter. buzz-agent's own reaping is Unix process groups (`crates/buzz-agent/src/mcp.rs:131,152-153`) and does not carry to Windows, which reaps no descendants and lets an ordinarily spawned child run before assignment. `crates/buzz-dev-mcp/src/shell.rs:763-790` is the shape to copy for the Job Object calls, not the error handling: it discards the return value of `SetInformationJobObject` (783-788) and of `AssignProcessToJobObject` (790). A tolerated containment failure leaks whole process trees (AGENTS.md Review-Proven Rule 4).

**4 · HTTP credentials and the proxy boundary.**
Decision: the same binary in proxy mode runs as a local stdio MCP server, resolves its one bound secret through the capability of decision 5 at first use, and forwards to the Streamable HTTP upstream with the header attached. No generated JSON or TOML holds a secret value. The upstream URL must be `https://`, the single exception being a loopback host (`127.0.0.1`, `::1`, `localhost`); URL userinfo is rejected at load, and a credential-shaped query string is rejected per entry under decision 5. Redirects are disabled — a 30x is returned as an error, never followed, so no origin change can carry the credential. The header name comes from a pinned map over a small enumerated set of auth schemes, never from operator free text. Connect timeout 10 s, whole-request timeout 60 s, response body capped at 4 MiB, each breach a distinct named error. Aggregate bounds: MCP stdio is newline-delimited JSON and carries no length prefix, so the inbound bound is a bounded newline decoder — `JsonRpcMessageCodec::new_with_max_length` at 1 MiB, or an equivalent bounded reader — applied before any JSON deserialization; plus 1 MiB max outgoing request body, 16 in-flight requests, 8 upstream connections, 32 MiB buffered in total, with reads paused rather than queued once that ceiling is reached. Tests: a non-loopback `http://` URL is refused at load; a userinfo URL is refused; a 302 returns an error and issues no second request; a header name outside the pinned map is refused; a body past the cap aborts the call; a hung upstream trips connect and request timeouts; more than 1 MiB with no newline and more than 1 MiB followed by a newline are both refused through the shipped transport; 64 concurrent callers are served under the in-flight cap with bounded memory and no unbounded queue.
Reason: no launcher can inject an environment into a remote server, and Claude's `.mcp.json` and Codex's `config.toml` are plaintext files on disk that the config panel also reads back (decision 9). Once the proxy holds a resolved credential, the scheme, the redirect policy and the header name decide who receives it. The bound has to be constructed explicitly: this workspace resolves `rmcp` 1.8.0 (`Cargo.lock:7959-7960`), whose newline codec defaults to `usize::MAX`, so the shipped default is no bound at all.

**5 · Where secrets live.**
Decision: extract a workspace crate `crates/buzz-secret-store` carrying the read side of today's keychain blob; the desktop keeps the write side. Every secret is stored under a reserved `mcp:` namespace and bound to the pair (agent id, configuration generation of decision 8); the desktop generates the id and an operator never chooses it. A raw `mcp:` id authorizes nothing. **The v1 authorization boundary is the agent, not the server.** For each spawn the desktop mints one unguessable per-agent, per-spawn capability for the current generation and places it in the spawn environment (`desktop/src-tauri/src/managed_agents/runtime.rs:563`); buzz-acp inherits it, buzz-agent and the native adapter chain forward it, and `buzz-mcp-launch` strips it from its own environment before it starts the server. The extracted crate exposes one typed lookup that takes a capability and resolves only the secrets bound to that agent; it accepts no name, and can address no other agent's key. Cross-server isolation within one agent is out of scope for v1 (risk below). Credentials are their own typed Settings field, stored only in the secret store: an entry's argv and its URL query string are scanned for sentinel credential patterns and refused per entry under decision 7 with a surfaced status, so no credential is written to a generated file. The desktop write path applies the same binding and rejects `identity`, any `agent:*` name, and any reference without an `mcp:` prefix. Deleting a server or an agent revokes its capabilities and removes its bound secrets, as a decision-8 journal entry retried while that entry is `FLIPPED`; convergence also terminates the affected launcher and proxy processes, and until that completes the panel shows the entry as pending restart. Blob bounds: each agent may enable at most 16 servers, the shared store holds at most 256 MCP secret records globally, 8 KiB per value and 1 MiB for the whole blob, each overflow a surfaced error rather than a larger entry. Tests: `capability_cannot_cross_agents`, `post_flip_cleanup_resumes` and `deleted_server_stops_authenticating` below.
Reason: `secret_store` is a private Tauri module (`desktop/src-tauri/src/lib.rs:43`) that a workspace binary cannot call, and the blob is one keychain entry costing one OS prompt per process (`desktop/src-tauri/src/secret_store.rs:3-6`) that also holds the human nsec under `identity` (`desktop/src-tauri/src/app_state.rs:307`) and every agent nsec under `agent:<pubkey>` (`desktop/src-tauri/src/managed_agents/storage.rs:16-19`). An unreserved namespace would let `MY_TOKEN=keychain:identity` on an untrusted server read the human key, and buzz-agent's identity filter cannot stop it: it matches on variable name only (`crates/buzz-agent/src/mcp.rs:1009-1014`). A namespace alone is still not an authorization boundary, because an id is only a name. The spawn environment is the one channel every hop of the chain already propagates unchanged, which is why the capability is per agent: a per-server capability would have to reach each server through the plaintext native config the adapter reads, where any server keeping `HOME` (risk below) could lift it. `load_blob` deserializes the entire map on every read (`desktop/src-tauri/src/secret_store.rs:310`), so an uncapped secret count is an uncapped per-read cost as well as an unbounded keychain entry.

**6 · Launcher crate path and packaging.**
Decision: `crates/buzz-mcp-launch`, added to the workspace members (`Cargo.toml:2-34`), the stub list (`Justfile:167-180`), both release build recipes (`Justfile:281-295`, `Justfile:312-315`), `SIDECARS` in `scripts/bundle-sidecars.sh:4` and both `BUILD_HINT` lines beside it (`scripts/bundle-sidecars.sh:9,11`), `externalBin` in `desktop/src-tauri/tauri.conf.json:55-62` and in the Windows manifest `desktop/src-tauri/tauri.windows.conf.json:3-9`, which replaces that array rather than extending it, and every CI sidecar build command: `.github/workflows/release.yml:94,311,566,715`, `linux-canary.yml:189`, `windows-canary.yml:144`, `signed-macos-canary.yml:118`, `macos-intel-canary.yml:86`. Generated config names the resolved absolute path of the bundled binary, never a bare name.
Reason: the `externalBin` lists must agree with what is built or the Tauri build fails at compile time on validation — and the Windows manifest is a replacement, so a base-list-only edit ships a Windows build without the launcher. Adding it to `SIDECARS` without adding it to every build command trips the missing-binary gate (`scripts/bundle-sidecars.sh:31-39`). A bare name would resolve through a `PATH` the launcher's own clear removes.

**7 · Name collisions, rejection semantics and registry bounds.**
Decision: the loader rejects at load any server name equal to a built-in server's name or carrying the reserved `buzz-` prefix, and never renames silently. Every entry also carries a stable unique id and emits a unique name, both checked case-insensitively across the whole document before any file is written. Exactly three failures reject the whole document: a duplicate id or name, the 256 KiB document cap, and the 4 KiB single-entry cap — the duplicate because which of two colliding entries survives is order-dependent, the two caps because a truncated registry is not a safe partial. Every other validation failure is per entry — an http entry on buzz-agent, a non-loopback `http://` URL, an unapproved proxy value, a sentinel credential in argv or in a URL query: the entry is disabled and carries a status string the Settings panel renders beside it, the rest of the registry loads, and an agent that has a rejected entry toggled on refuses to spawn with that same message rather than starting silently short a server. A `tracing::warn` is not a refusal. The registry inherits buzz-acp's cap of 16 servers per agent. The document is opened no-follow (`O_NOFOLLOW`, `FILE_FLAG_OPEN_REPARSE_POINT` on Windows) and read to at most 256 KiB plus one byte before any UTF-8 decoding or parsing; a read that fills that buffer is over the cap. Tests: the same two colliding entries in either order reject identically for the JSON, TOML and buzz-acp targets; a sparse multi-gigabyte registry file is rejected without allocating it.
Reason: buzz-acp resolves a collision by appending a hash suffix (`crates/buzz-acp/src/lib.rs:6168-6173`, having detected it at 6162-6167), which changes the qualified tool name the model calls — a correct last resort for a parsed env var, wrong for a registry the operator can edit. Both native targets key servers by name — Claude a JSON `mcpServers` object (`desktop/src-tauri/src/managed_agents/config_bridge/claude.rs:50`), Codex an `mcp_servers` TOML table (`config_bridge/codex.rs:70-71`) — so two entries named `github` serialize to one key and one command silently keeps the other's credential. The `custom_harnesses` bar logs and skips per file by documented design (`desktop/src-tauri/src/managed_agents/custom_harnesses.rs:72-77,110-117`) and reads each file with an unbounded `read_to_string` (`custom_harnesses.rs:110`), so the registry takes its structure and neither its silence nor its read; the 16-server cap is buzz-acp's (`crates/buzz-acp/src/lib.rs:5888`, documented at `crates/buzz-acp/src/config.rs:284-286`).

**8 · Per-agent toggle storage.**
Decision: the enabled-server list is a new optional, versioned field on the agent record in `managed-agents.json` — absent means "no registry servers" and is a distinct state from an empty list, so a later default change reads the version rather than reinterpreting absence — and it is deliberately not added to the kind:30177 projection. Renaming or deleting a registry server drops its id from every agent record. All of it moves as one configuration generation: the registry document, every regenerated per-agent config and every affected agent record are staged under a fresh `generations/<n>/` directory, and that generation is adopted by renaming one pointer onto `current` while the spawn lock is held. Spawn resolves every path through the pointer and never through a staged directory, so it always reads one generation whole. A durable journal records the intent in three phases, each fsynced before the next step begins: `PREPARED` before the first write, `FLIPPED` immediately after the pointer rename, `CLEANED` once every post-flip deletion — generated files, agent-record edits and keychain removals alike — has succeeded. The entry is removed only at `CLEANED`; the next start finds `PREPARED` with no flip and discards the half-staged generation, or finds `FLIPPED` and retries every deletion it committed until they all succeed. One configuration-mutation lock is held from the base-generation read through `CLEANED`, so two concurrent Settings actions cannot both stage from generation N and flip in turn: the loser waits, re-reads the new base and restages, and no user action is silently discarded. Retention is bounded at current plus one rollback generation; retiring the older directory is itself a journaled step, and startup reconciles whatever a crash left behind, so the staging tree never holds more than two generations.
Reason: that projection is an opt-in, field-by-field allowlist (`desktop/src-tauri/src/managed_agents/agent_events.rs:38`, `desktop/src-tauri/src/managed_agents/reconcile.rs:59-61`), so a new field stays machine-local unless someone adds it — and this design does not. Ordering the writes is not enough: dropping a server from the registry first leaves agents launching from old generated configs that still name it, and adding one exposes a generated config before the record that enables it, so some prefix is always torn and two agents can sit on different generations. One pointer rename is the only write the whole set can share, and a journal cleared at that rename would strand a credential whose keychain delete failed a moment later. AGENTS.md Review-Proven Rules 1, 2 and 5 require the durable retry, the cleared derived state on every removal path, and one atomic persist per user action.

**9 · Config roots per agent, with the T6 login caveat.**
Decision: the config root is per agent and is created on the spawn path — each agent gets its own working directory under the nest instead of the shared `~/.buzz`, and Claude's project `.mcp.json` is written there; `CLAUDE_CONFIG_DIR` stays unset. The config bridge becomes placement-aware in the same change: it reads that agent's project file from the per-agent workdir rather than the home config it reads today, so the panel reports the file Claude actually loads. This is also what unblocks T6's per-agent scope, impossible today. Claude registry support stays off until an isolated root that preserves the login is proven on a real launch: until then the panel shows Claude as unavailable rather than writing a shared file. Codex stays unavailable for the same reason — writing the operator's `~/.codex/config.toml` would hand one agent's servers to every Codex process on the machine — until a Dock launch proves a login survives a per-agent `CODEX_HOME`. Test `the toggle changes only the named agent's generated config` spawns two agents of one runtime with different toggles and asserts their generated config files are at distinct paths, each holds exactly its own server set, and toggling one leaves the other's file byte-identical.
Reason: `default_agent_workdir()` is a process-wide `OnceLock` returning one path for every agent (`desktop/src-tauri/src/managed_agents/mod.rs:130-143`) and every spawn sets it as cwd (`desktop/src-tauri/src/managed_agents/runtime.rs:563-565`), so a shared root is last-writer-wins: agent B inherits agent A's approved servers, including a credential-resolving proxy entry. The bridge today resolves `.claude.json` from `CLAUDE_CONFIG_DIR` or `$HOME` (`desktop/src-tauri/src/managed_agents/config_bridge/claude.rs:23-25`), which with that variable unset is the operator's own file, not the generated one. A custom `CLAUDE_CONFIG_DIR` creates a fresh keychain namespace and leaves Claude logged out unless `CLAUDE_SECURESTORAGE_CONFIG_DIR` is managed too (`desktop/src-tauri/src/managed_agents/config_bridge/types.rs:191-197`, `desktop/src/features/agents/ui/AgentConfigPanel.tsx:292-312`); `codex_config_path()` falls back to `~/.codex/config.toml` whenever `CODEX_HOME` is unset (`desktop/src-tauri/src/managed_agents/config_bridge/codex.rs:125-131`).

**10 · Per-server environment on the buzz-agent path.**
Decision: buzz-agent servers are declared from the registry with an `env` block carrying `mcp:` references, never values, and the registry never generates a `BUZZ_ACP_EXTRA_MCP_COMMANDS` argv. The handoff is a structured one: a new variable `BUZZ_ACP_MCP_REGISTRY` names a file, a bounded JSON document holding each server's name, command, args and reference-valued `env`, which buzz-acp reads at startup and turns into `McpServer` entries. That file carries references only; the capability of decision 5 never appears in it and reaches the launcher through the inherited spawn environment instead. buzz-acp resolves nothing; the launcher of decision 3, which is the command on every generated entry, is the side that resolves — so no resolved value ever enters buzz-acp's address space or the ACP wire. On top of that, the `acp::wire` logging seam redacts structurally: the serializer used for that log replaces every `mcpServers[].env[].value` with a fixed placeholder, rather than relying on the seam staying at `info`.
Reason: an entry's argv is readable by `ps` and by any crash dump, which the config surface itself warns (`crates/buzz-acp/src/config.rs:284-286`) — hence the argv sentinel scan of decision 5. The extras path hardcodes `env: vec![]` with `trusted: false` (`crates/buzz-acp/src/lib.rs:6191-6196`), so it cannot carry the block at all. `send_request` logs the whole serialized message and `McpServer.env` is not skipped (`crates/buzz-acp/src/acp.rs:44,1127`). The declared `env` block is filtered on the same identity rule as the ambient one (`crates/buzz-agent/src/mcp.rs:835-846`).

**11 · Capability facts.**
Decision: `mcp_config_root_env` is replaced by `mcp_config_placement`, a strategy value every `KnownAcpRuntime` entry must fill — `ProjectFileInWorkdir { file }` for Claude, `EnvRootedDir { var, file }` for Codex, `Unsupported` for goose and any runtime with no native MCP config — and `mcp_transports` (what the registry may offer a runtime) is kept separate from `mcp_native_transports` (what that runtime's own config accepts). Add all three, expose them on `AcpRuntimeCatalogEntry`, project them through the core, and update the feature guide in the same PR. The readback of decision 9 reads the same placement value, so the panel and the writer cannot drift.
Reason: `KnownAcpRuntime` is a static struct with no defaults (`desktop/src-tauri/src/managed_agents/discovery/runtime_metadata.rs:68`), and an env-var *name* cannot express Claude's cwd-relative project file with `CLAUDE_CONFIG_DIR` deliberately unset, nor Codex's "supported only after Dock-login verification". The guide makes the Rust runtime catalog the single source of harness capability facts and forbids a rival TypeScript table (`desktop/src/features/agents/AGENTS.md:13,34`).

## Regression tests at the production seam

Each names the production entry point it drives; deleting the guard it names fails it.

- `grandchild_dies_with_adapter` — the fixture double-forks, calls `setsid()` and closes its inherited pipes; run through the shipped launcher, it asserts no survivor on Linux under the leaf cgroup and asserts the documented macOS residue exactly, so a silent change in either direction fails (decision 3).
- `job_object_failure_leaves_no_process` — an injected `SetInformationJobObject` failure before `ResumeThread` in the shipped launcher leaves no running process (decision 3).
- `capability_cannot_cross_agents` — two agents spawned through `runtime.rs:563` and the real adapter chain; agent A's harness cannot resolve agent B's secrets, `identity`, or `agent:*`, and cannot be handed a whole key (decision 5).
- `stdio_frame_bound_holds` — through the shipped proxy transport and its real newline decoder, more than 1 MiB with no newline and more than 1 MiB followed by a newline are both refused (decision 4).
- `wire_log_redacts_env_values` — the serializer behind `acp::wire` (`crates/buzz-acp/src/acp.rs:1127`) emits the placeholder for every `mcpServers[].env[].value` (decision 10).
- `generation_flip_is_atomic` — failure injected before and after every decision-8 write and every journal transition, with a spawn attempted at each intermediate point (decision 8).
- `post_flip_cleanup_resumes` — a keychain delete failing after `FLIPPED` is retried against the real store on the next start until `CLEANED` (decisions 5, 8).
- `two_writers_serialize` — two concurrent Settings mutations from one base generation reach the real mutation lock; the loser restages and neither action is lost (decision 8).
- `deleted_server_stops_authenticating` — an authenticated request through a live proxy after its server is deleted fails once convergence terminates that process, and the panel reads pending restart until then (decision 5).
- `claude_readback_uses_the_agent_workdir` — the actual Settings panel command reads the generated project file from the per-agent workdir, not `$HOME` (decision 9).
- `rejected_entry_blocks_spawn` — a sentinel credential in argv and one in a URL query each reject that entry through the shipped loader, reach the Settings status string and refuse that agent's spawn, while the rest of the registry loads (decisions 5, 7).

## Supersedes

The T7 clauses in `docs/plans/2026-09-04-zs-implementation-plan.md` naming `BUZZ_ACP_EXTRA_MCP_COMMANDS`, a per-agent `CLAUDE_CONFIG_DIR` and `mcp_config_root_env` are superseded by decisions 10, 9 and 11 of this memo.

Within this memo, decision 3's Windows mechanism — `CREATE_SUSPENDED`, `AssignProcessToJobObject`, `ResumeThread` — is superseded by the shipped shape amended into decision 3 on 2026-09-05 (T7b): the launcher joins the kill-on-close Job Object itself before it spawns the server. The guarantee is unchanged; only the mechanism is.

## Open verifications

Only a run can settle these; each blocks the decision it names, not the memo.

- Codex login under a per-agent `CODEX_HOME` from a Dock launch — the T6 caveat carried over from Claude. Until it passes, Codex registry support stays unavailable (decision 9).
- Whether Claude 2.1.x loads a project `.mcp.json` from a per-agent working directory without a first-spawn trust prompt, and whether its login survives that root (decision 9).
- That a per-agent working directory does not break code that assumes every agent runs in `~/.buzz` (decision 9).
- That the resident launcher's stdio relay leaves the server's pipes intact end to end on Unix, and that it can create a cgroup v2 leaf on the Linux targets we ship to (decision 3).
- That the extracted crate reads the same keychain blob a signed release build wrote — macOS splits SecKeychain and DPK (`desktop/src-tauri/src/secret_store.rs:8-12`, decision 5).

## Risks accepted

- Cross-server isolation within one agent is not in v1: every server an agent enables can redeem that agent's capability. There is no per-server channel to build one on — the servers keep `HOME` and the native adapters spawn from plaintext config, so a per-server secret would have to be readable by every server the adapter starts. Closing it needs an authenticated broker the launcher talks to instead of a shared store; that is the v2 path.
- The launcher is not process isolation: the server still runs under the user's UID and keeps `HOME`, so it reads whatever the user can — the limit buzz-agent already documents (`crates/buzz-agent/src/mcp.rs:812-814`).
- On macOS, and on Linux without cgroup v2, a server that double-forks and calls `setsid()` escapes the launcher's `killpg` and survives the adapter (decision 3).
- A third-party ACP adapter that spawns its own MCP children stays out of reach; only servers Buzz generates config for get the launcher.
- The proxy holds a resolved credential in memory until convergence terminates it, so a dump of a live proxy exposes it, and a deleted server keeps authenticating for the pending-restart window.
- Generated command lines remain readable by anything running as the user; the design moves secret values out of them, not the commands themselves.
- The config bridge reads back only name, kind and enabled (`desktop/src-tauri/src/managed_agents/config_bridge/types.rs:226-233`), so the panel cannot detect a wrong generated command; tests assert the written files structurally instead.
- Shipping Claude and Codex registry support off (decision 9) means the first release exercises the buzz-agent path only; the proxy and native-config generation land behind a verification that has not run yet.
