# MCP registry — design memo (T7)

Date: 2026-09-04. Answers the checklist in `docs/plans/2026-09-04-zs-implementation-plan.md` § T7
and the four BLOCK, eight WARN and three NIT findings of the Sol audit. Every `file:line` below was
read against this branch's tree at `6badf5112`.

**1 · Server classes and the environment each receives.**
Decision: two classes — `stdio` (command, args, `env` block) and `http` (Streamable HTTP URL, no `env`). A stdio server's child environment is built from empty and receives exactly one enumerated list plus its own approved `env` values: `PATH`, `HOME` (`USERPROFILE` and `SystemRoot` on Windows), `TMPDIR` (`TEMP` and `TMP` on Windows), `LANG`, `LC_ALL`, `TERM`, the eight proxy spellings, `SSL_CERT_FILE` and `SSL_CERT_DIR`. The approved values win on a name clash. The credential handles and command overrides in buzz-agent's own list — `SSH_AUTH_SOCK`, `SSH_AGENT_PID`, `GIT_ASKPASS`, `GIT_SSH_COMMAND`, `GIT_CONFIG_GLOBAL`, `XDG_CONFIG_HOME` — are deliberately excluded, and a registry command must be an absolute path: the `PATH` above is for the child's own subprocesses, never for resolving the command. An http upstream gets no environment; its credential travels as a request header injected at call time.
Reason: the ACP wire carries the stdio shape alone (`crates/buzz-acp/src/acp.rs:40`, `crates/buzz-agent/src/types.rs:537`), and an http upstream has no child process to hand variables to. buzz-agent's `PASSTHROUGH_ENV` (`crates/buzz-agent/src/mcp.rs:39-97`) is an allow-list for a child it trusts; copying it whole under the word "essentials" would contradict "nothing else".

**2 · Runtime capability matrix.**
Decision: buzz-agent — stdio only; an http entry is rejected under decision 7's semantics, never silently dropped. Claude and Codex — stdio and http, http reached through the proxy of decision 4, both subject to the availability rule in decision 9.
Reason: `McpServerStdio` is the only server variant buzz-agent deserializes (`crates/buzz-agent/src/types.rs:537`). Claude and Codex read native config files; today the bridge only reads them (`desktop/src-tauri/src/managed_agents/config_bridge/claude.rs:14` is `read_config_file`, `codex.rs:125` is `codex_config_path`, and the module has no `fs::write` path at all), so writing those files is this ticket's new work, not existing behaviour.

**3 · Process boundary for stdio servers under Claude and Codex.**
Decision: every generated stdio entry names a bundled launcher, `buzz-mcp-launch`, as its command. The launcher clears the inherited environment, adds only decision 1's list and the server's approved values, then `exec`s the server on Unix. On Windows it creates a kill-on-close Job Object, assigns itself and the server to it, and holds the job handle for its own lifetime, so the whole tree dies when the handle closes. Job Object creation, `SetInformationJobObject` and `AssignProcessToJobObject` failure is a startup error: the launcher exits non-zero and starts no server.
Reason: the adapter is spawned with no `env_clear` and inherits the harness environment including provider keys and user-defined values (`crates/buzz-acp/src/acp.rs:470`, `desktop/src-tauri/src/managed_agents/runtime.rs:693-695`), so any MCP child it spawns inherits them too. The pattern is buzz-agent's own (`crates/buzz-agent/src/mcp.rs:798,808`). Windows has no `exec` and does not reap descendants, and buzz-agent's reaping is Unix process groups; the repo already carries the correct Windows pattern (`crates/buzz-dev-mcp/src/shell.rs:763-790` — `CreateJobObjectW`, `SetInformationJobObject` with `JobObjectExtendedLimitInformation`, `AssignProcessToJobObject`). A tolerated containment failure leaks whole process trees (AGENTS.md Review-Proven Rule 4).

**4 · HTTP credentials and the proxy boundary.**
Decision: the same binary in proxy mode runs as a local stdio MCP server, resolves the keychain reference at first use, and forwards to the Streamable HTTP upstream with the header attached. No generated JSON or TOML holds a secret value. The upstream URL must be `https://`, the single exception being a loopback host (`127.0.0.1`, `::1`, `localhost`); URL userinfo is rejected at load. Redirects are disabled — a 30x is returned as an error, never followed, so no origin change can carry the credential. The header name comes from a pinned map over a small enumerated set of auth schemes, never from operator free text. Connect timeout 10 s, whole-request timeout 60 s, response body capped at 4 MiB, each breach a distinct named error. Tests: a non-loopback `http://` URL is refused at load; a userinfo URL is refused; a 302 returns an error and issues no second request; a header name outside the pinned map is refused; a body past the cap aborts the call; a hung upstream trips connect and request timeouts.
Reason: no launcher can inject an environment into a remote server, and Claude's `.mcp.json` and Codex's `config.toml` are plaintext files on disk that the config panel also reads back. Once the proxy holds a resolved credential, the scheme, the redirect policy and the header name decide who receives it.

**5 · Where secrets live.**
Decision: extract a workspace crate `crates/buzz-secret-store` carrying the read side of today's keychain blob; the desktop keeps the write side. Registry `env` values and http credentials are stored under a reserved `mcp:<opaque-id>` namespace, the id generated by the desktop and never operator-chosen, and referenced as `mcp:<opaque-id>` — never as a literal. The extracted crate exposes one typed MCP-only lookup that takes an opaque id, prefixes `mcp:` itself, and can address no other key; the desktop write path applies the same prefix. Both paths reject `identity`, any `agent:*` name, and any reference without an `mcp:` prefix. Test `mcp_reference_namespace_is_closed` asserts that `identity`, `agent:<pubkey>`, a bare name, and an `mcp:` id containing a separator are each rejected on the read path and on the write path, and that the typed lookup cannot be handed a whole key.
Reason: `secret_store` is a private Tauri module (`desktop/src-tauri/src/lib.rs:43`) that a workspace binary cannot call, and the blob is one keychain entry costing one OS prompt per process (`desktop/src-tauri/src/secret_store.rs:3-6`) that also holds the human nsec under `identity` (`desktop/src-tauri/src/app_state.rs:307`) and every agent nsec under `agent:<pubkey>` (`desktop/src-tauri/src/managed_agents/storage.rs:16-19`). An unreserved namespace would let `MY_TOKEN=keychain:identity` on an untrusted server read the human key, and buzz-agent's identity filter cannot stop it: it matches on variable name only (`crates/buzz-agent/src/mcp.rs:1009-1014`).

**6 · Launcher crate path and packaging.**
Decision: `crates/buzz-mcp-launch`, added to the workspace members (`Cargo.toml:2-32`), the stub list (`Justfile:167-180`), both release build recipes (`Justfile:281-295`, `Justfile:312-315`), `SIDECARS` in `scripts/bundle-sidecars.sh:4` and both `BUILD_HINT` lines beside it (`scripts/bundle-sidecars.sh:9,11`), `externalBin` in `desktop/src-tauri/tauri.conf.json:55-62` and in the Windows manifest `desktop/src-tauri/tauri.windows.conf.json:3-9`, which replaces that array rather than extending it, and every CI sidecar build command: `.github/workflows/release.yml:94,311,566,715`, `linux-canary.yml:189`, `windows-canary.yml:144`, `signed-macos-canary.yml:118`, `macos-intel-canary.yml:86`. Generated config names the resolved absolute path of the bundled binary, never a bare name.
Reason: the `externalBin` lists must agree with what is built or the Tauri build fails at compile time on validation — and the Windows manifest is a replacement, so a base-list-only edit ships a Windows build without the launcher. Adding it to `SIDECARS` without adding it to every build command trips the missing-binary gate (`scripts/bundle-sidecars.sh:31-35`). A bare name would resolve through a `PATH` the launcher's own clear removes.

**7 · Name collisions, rejection semantics and registry bounds.**
Decision: the loader rejects at load any server name equal to a built-in server's name or carrying the reserved `buzz-` prefix, and never renames silently. Rejection is per entry: the entry is disabled and carries a status string the Settings panel renders beside it, the rest of the registry loads, and an agent that has a rejected entry toggled on refuses to spawn with that same message rather than starting silently short a server. A `tracing::warn` is not a refusal. The registry inherits buzz-acp's cap of 16 servers per agent and adds a 256 KiB cap on the document and a 4 KiB cap on a single entry; over either, the whole file is rejected with a surfaced status, because a truncated registry is not a safe partial.
Reason: buzz-acp resolves a collision by appending a hash suffix (`crates/buzz-acp/src/lib.rs:6168-6173`, having detected it at 6162-6167), which changes the qualified tool name the model calls — a correct last resort for a parsed env var, wrong for a registry the operator can edit. The `custom_harnesses` bar logs and skips per file by documented design (`desktop/src-tauri/src/managed_agents/custom_harnesses.rs:72-77,110-117`) and reads each file unbounded, so the registry takes its structure and not its silence; the 16-server cap is buzz-acp's (`crates/buzz-acp/src/lib.rs:5888`, documented at `crates/buzz-acp/src/config.rs:284-286`).

**8 · Per-agent toggle storage.**
Decision: the enabled-server list is a new optional, versioned field on the agent record in `managed-agents.json` — absent means "no registry servers" and is a distinct state from an empty list, so a later default change reads the version rather than reinterpreting absence — and it is deliberately not added to the kind:30177 projection. Renaming or deleting a registry server drops its id from every agent record in the same write. Write order is: registry document, then each affected agent's regenerated config, then the agent records. Every prefix of that order leaves an agent on its old server set or its new one and never referencing a server the registry no longer holds; a failure part-way is retried from the registry, which is the source of truth.
Reason: that projection is an opt-in, field-by-field allowlist (`desktop/src-tauri/src/managed_agents/agent_events.rs:70-80`, `desktop/src-tauri/src/managed_agents/reconcile.rs:59-61`), so a new field stays machine-local unless someone adds it — and this design does not. AGENTS.md Review-Proven Rules 1 and 2 require the durable retry and the cleared derived state on every removal path.

**9 · Config roots per agent, with the T6 login caveat.**
Decision: the config root is per agent and is created on the spawn path — each agent gets its own working directory under the nest instead of the shared `~/.buzz`, and Claude's project `.mcp.json` is written there; `CLAUDE_CONFIG_DIR` stays unset. This is also what unblocks T6's per-agent scope, impossible today. Claude registry support stays off until an isolated root that preserves the login is proven on a real launch: until then the panel shows Claude as unavailable rather than writing a shared file. Codex stays unavailable for the same reason — writing the operator's `~/.codex/config.toml` would hand one agent's servers to every Codex process on the machine — until a Dock launch proves a login survives a per-agent `CODEX_HOME`. Test `the toggle changes only the named agent's generated config` spawns two agents of one runtime with different toggles and asserts their generated config files are at distinct paths, each holds exactly its own server set, and toggling one leaves the other's file byte-identical.
Reason: `default_agent_workdir()` is a process-wide `OnceLock` returning one path for every agent (`desktop/src-tauri/src/managed_agents/mod.rs:130-143`) and every spawn sets it as cwd (`desktop/src-tauri/src/managed_agents/runtime.rs:563-565`), so a shared root is last-writer-wins: agent B inherits agent A's approved servers, including a credential-resolving proxy entry. A custom `CLAUDE_CONFIG_DIR` creates a fresh keychain namespace and leaves Claude logged out unless `CLAUDE_SECURESTORAGE_CONFIG_DIR` is managed too (`desktop/src-tauri/src/managed_agents/config_bridge/types.rs:191-197`, `desktop/src/features/agents/ui/AgentConfigPanel.tsx:292-312`); `codex_config_path()` falls back to `~/.codex/config.toml` whenever `CODEX_HOME` is unset (`desktop/src-tauri/src/managed_agents/config_bridge/codex.rs:125-131`).

**10 · Per-server environment on the buzz-agent path.**
Decision: buzz-agent servers are declared from the registry with an `env` block carrying `mcp:` references, never values, and the registry never generates a `BUZZ_ACP_EXTRA_MCP_COMMANDS` argv. The handoff is a structured one: a new variable `BUZZ_ACP_MCP_REGISTRY` names a file, a bounded JSON document holding each server's name, command, args and reference-valued `env`, which buzz-acp reads at startup and turns into `McpServer` entries. buzz-acp resolves nothing; the launcher of decision 3, which is the command on every generated entry, is the side that resolves — so no resolved value ever enters buzz-acp's address space or the ACP wire. On top of that, the `acp::wire` logging seam redacts structurally: the serializer used for that log replaces every `mcpServers[].env[].value` with a fixed placeholder, rather than relying on the seam staying at `info`.
Reason: an entry's argv is readable by `ps` and by any crash dump, which the config surface itself warns (`crates/buzz-acp/src/config.rs:284-286`). The extras path hardcodes `env: vec![]` with `trusted: false` (`crates/buzz-acp/src/lib.rs:6191-6196`), so it cannot carry the block at all. `send_request` logs the whole serialized message and `McpServer.env` is not skipped (`crates/buzz-acp/src/acp.rs:44,1127`). The declared `env` block is filtered on the same identity rule as the ambient one (`crates/buzz-agent/src/mcp.rs:835-846`).

**11 · Capability facts.**
Decision: `mcp_config_root_env` is replaced by `mcp_config_placement`, a strategy value every `KnownAcpRuntime` entry must fill — `ProjectFileInWorkdir { file }` for Claude, `EnvRootedDir { var, file }` for Codex, `Unsupported` for goose and any runtime with no native MCP config — and `mcp_transports` (what the registry may offer a runtime) is kept separate from `mcp_native_transports` (what that runtime's own config accepts). Add all three, expose them on `AcpRuntimeCatalogEntry`, project them through the core, and update the feature guide in the same PR.
Reason: `KnownAcpRuntime` is a static struct with no defaults (`desktop/src-tauri/src/managed_agents/discovery/runtime_metadata.rs:68`), and an env-var *name* cannot express Claude's cwd-relative project file with `CLAUDE_CONFIG_DIR` deliberately unset, nor Codex's "supported only after Dock-login verification". The guide makes the Rust runtime catalog the single source of harness capability facts and forbids a rival TypeScript table (`desktop/src/features/agents/AGENTS.md:13,34`).

## Open verifications

Only a run can settle these; each blocks the decision it names, not the memo.

- Codex login under a per-agent `CODEX_HOME` from a Dock launch — the T6 caveat carried over from Claude. Until it passes, Codex registry support stays unavailable (decision 9).
- Whether Claude 2.1.x loads a project `.mcp.json` from a per-agent working directory without a first-spawn trust prompt, and whether its login survives that root (decision 9).
- That a per-agent working directory does not break code that assumes every agent runs in `~/.buzz` (decision 9).
- That `exec` through the launcher leaves the server's stdio pipes intact end to end on Unix (decision 3).
- That the launcher's Job Object reaps the server when the adapter is killed on Windows (decision 3).
- That the extracted crate reads the same keychain blob a signed release build wrote — macOS splits SecKeychain and DPK (`desktop/src-tauri/src/secret_store.rs:8-12`, decision 5).

## Risks accepted

- The launcher is not process isolation: the server still runs under the user's UID and keeps `HOME`, so it reads whatever the user can — the limit buzz-agent already documents (`crates/buzz-agent/src/mcp.rs:812-814`).
- A third-party ACP adapter that spawns its own MCP children stays out of reach; only servers Buzz generates config for get the launcher.
- The proxy holds a resolved credential in memory for the session's life, so a dump of the proxy exposes it.
- Generated command lines remain readable by anything running as the user; the design moves secret values out of them, not the commands themselves.
- The config bridge reads back only name, kind and enabled (`desktop/src-tauri/src/managed_agents/config_bridge/types.rs:226-233`), so the panel cannot detect a wrong generated command; tests assert the written files structurally instead.
- Shipping Claude and Codex registry support off (decision 9) means the first release exercises the buzz-agent path only; the proxy and native-config generation land behind a verification that has not run yet.
