## Route (a): webview print-to-PDF behind a Tauri command — not measurable, disqualified

This app pins `tauri = "2"` → `tauri 2.11.5` → `wry 0.55.1`
(`desktop/src-tauri/Cargo.lock`). Tauri's `WebviewWindow::print()` forwards to
`wry`'s webview `print()` on desktop. Quoted in full below, not excerpted —
read directly from the pinned `wry` source
(`~/.cargo/registry/src/.../wry-0.55.1/src/wkwebview/mod.rs:858-898`, macOS
backend):

```rust
pub fn print(&self) -> crate::Result<()> {
  self.print_with_options(&PrintOptions::default())
}

pub fn print_with_options(&self, _options: &PrintOptions) -> crate::Result<()> {
  // Safety: objc runtime calls are unsafe
  #[cfg(target_os = "macos")]
  unsafe {
    // <https://developer.apple.com/documentation/webkit/wkwebview/printoperation(with:)>
    // Available: macOS 11+
    let can_print = self
      .webview
      .respondsToSelector(objc2::sel!(printOperationWithPrintInfo:));
    if can_print {
      // Create a shared print info
      let print_info = objc2_app_kit::NSPrintInfo::sharedPrintInfo();
      print_info.setTopMargin(_options.margins.top.into());
      print_info.setRightMargin(_options.margins.right.into());
      print_info.setBottomMargin(_options.margins.bottom.into());
      print_info.setLeftMargin(_options.margins.left.into());

      // Create new print operation from the webview content
      let print_operation = self.webview.printOperationWithPrintInfo(&print_info);

      // Allow the modal to detach from the current thread and be non-blocker
      print_operation.setCanSpawnSeparateThread(true);

      // Launch the modal
      let window = self.webview.window().unwrap();
      print_operation.runOperationModalForWindow_delegate_didRunSelector_contextInfo(
        &window, None, None, std::ptr::null_mut(),
      )
    }
  }

  Ok(())
}
```

The `respondsToSelector` guard and the four margin setters were omitted from
this section's code block in an earlier draft; both are quoted here. The
guard does not change the conclusion below — when it is `false` the function
silently produces no output at all, which is a stricter failure than the
modal path, not an escape from it. `PrintOptions` (same file, line 127-129):

```rust
#[derive(Debug, Default, Clone)]
pub struct PrintOptions {
  pub margins: PrintMargin,
}
```

Three facts fall out of this, not from speculation:

1. **It is modal, not headless.** `runOperationModalForWindow_delegate_...`
   attaches an `NSPrintOperation` to a real, visible `NSWindow` and runs it as
   an application-modal sheet. There is no way to invoke it without a window
   on screen, and it returns to the caller once the modal is *dismissed* by
   a person (approving or canceling), not once a file exists.
2. **There is no bytes/file output path.** `PrintOptions` carries only print
   margins. Unlike Electron's `webContents.printToPDF()` or Chrome DevTools'
   `Page.printToPDF`, wry's wrapper does not expose a "print silently to a
   buffer" mode — the only supported outcome is the OS print panel, from
   which a human chooses "Save as PDF" themselves.
3. **The only way around (1) and (2) is to bypass wry and call
   `WKWebView.createPDF(configuration:completionHandler:)` directly**, which
   requires the same class of `unsafe` Objective-C interop wry uses
   internally. This repository's hard rule (`AGENTS.md` "Quality Gates": *no
   `unsafe` code*) forbids adding that in application code.

Given (1)-(3), route (a) cannot produce a PDF through a script — every
export requires a human to click through a native print sheet — so it has no
number to report for the pdftotext/pdftoppm/size/wall-time checks below. This
alone is disqualifying for an export feature (T9) that needs to run
unattended from a menu action and be exercised by an e2e spec. No live Tauri
command was built to reconfirm this: the pinned dependency source already
settles it conclusively, and standing up a windowed app in this environment
to re-derive the same fact from the same code path was not a good use of a
half-day spike budget. This is recorded as a proposed scope deviation, not
a gap glossed over — see deviation 3 in "Deviations from the ticket text"
above for what it costs T9 (unmeasured WebKit-vs-Chromium comparison) and
what does not depend on it (the route pick itself). It still needs Devin's
explicit sign-off (see "Owner sign-off needed" before "Pick") before it is
treated as settled.

## Route (b): Rust HTML-to-PDF crate — `headless_chrome` 1.0.22

`headless_chrome` (MIT, `scripts/pdf-spike` — a standalone Cargo project, not
a workspace member) drives a local Chrome/Chromium binary over the DevTools
Protocol and
calls `Page.printToPDF`, which *is* a headless, non-interactive, bytes-out
API — the thing route (a) is missing. Harness:
`scripts/pdf-spike/src/render_headless_chrome.rs`. It found Chrome via
`headless_chrome::browser::default_executable()` (`/Applications/Google
Chrome.app` on this machine — a real, separately-installed browser, not
bundled with the crate).

Launch options are deliberately narrow, checked directly against the pinned
crate source (`headless_chrome-1.0.22/src/browser/process.rs`): the sandbox
is left at its default (`sandbox: true` at `:184`; an earlier draft passed
`.sandbox(false)`, which appends `--no-sandbox --disable-setuid-sandbox`
at `:442-443` for no benefit here — nothing in this harness runs as root),
and `.ignore_certificate_errors(false)` is set explicitly rather than left
at the crate's own default (`ignore_certificate_errors: true` at `:192`,
which would append `--ignore-certificate-errors` at `:420-422` and accept
an unverified TLS connection to any remote host the page fetched). The
fixture's `<img>` no longer fetches a live remote host at all (see next
paragraph), so this option currently has nothing to verify against — it is
set as a default the harness should carry regardless of what a given
fixture happens to load, not tied to today's specific fixture content.

Offline mode is not a Chrome-launch flag any more — an earlier draft of this
harness used `--proxy-server=127.0.0.1:1` (an unreachable local port) to
black-hole every outbound request, but that only produces a broken-image
placeholder and a byte-count drop, both of which are equally consistent with
the image request never having been issued at all as with it being issued
and failing. Neither is a measurement of an attempt.

Instead, per the ticket text, the offline fixture's remote `<img>` points at
a local sentinel HTTP server (`scripts/pdf-spike/src/sentinel.rs`, a second
binary in the same throwaway crate) bound to `127.0.0.1:18391`. The sentinel
accepts every TCP connection, logs the peer address and request line to a
file, and refuses the request with `403 Forbidden` before closing the
connection — it never serves the image. `validate.sh` starts the sentinel,
waits for its readiness line on stdout, runs the offline render against
`fixtures/approval-offline.html`, then asserts the sentinel's log file is
non-empty before tearing it down. This is a measurement, not an inference:
the log line

```
1788514280113 refused peer=127.0.0.1:56230 request=GET /remote-image.png HTTP/1.1
```

is direct proof the renderer issued the request and the sentinel received
it, independent of anything the resulting PDF looks like. No firewall rules
are changed, matching the ticket's constraint.

The online fixture's `<img>` originally pointed at a live
`https://upload.wikimedia.org/...` URL. It now points at
`fixtures/remote-image.png` (same directory as the fixture, loaded
same-origin over `file://` — sha256
`c4e870d358d64ce677e958c156d0e3fba466993d8e915fc81c5dc64937a9b696`, a
one-time local copy of the same Wikimedia asset) instead of fetching a live
remote host on every run: no unverified-TLS surface for the harness to carry
(see the `ignore_certificate_errors` note above), no dependency on network
reachability at render time, and a hash-pinned input like every other part
of this fixture. "Online" now means "the image loads, because a real file
is there to load"; "offline" (below) means the sentinel refuses it. Neither
mode depends on outbound internet access any more — the earlier "online"
name is kept only because it is what `run_online`/`validate.sh` already call
it, not because it fetches anything remote.

The online side needs the mirror-image proof to the offline sentinel log:
not just that the image load was attempted, but that it actually *succeeded*
before the page was captured. An earlier version of this harness
synchronized on a flat `std::thread::sleep` before printing — 800ms, chosen
by feel, undisclosed inside the reported wall time. That is not a check: if
the image load had taken longer than
800ms or failed outright, the harness would still print whatever was on the
page at that instant and every downstream validator check (page count,
headings, table cells, code marker, PNG render) would still pass, because
none of them look at the image. The harness now awaits the fixture's
`<img class="remote">` element directly, in-page, via a
`load`/`error`-event `Promise` (`wait_for_remote_image` in
`render_headless_chrome.rs`), bounded by a 5s in-page timeout, and reports
the settled state — `loaded`, `failed`, `timeout`, or `missing` — as
`image_state` in the JSON line, timed separately (`image_wait_ms`) from the
print itself (`print_ms`). `validate.sh` asserts on that field: the online
run must see `image_state=loaded` or the run FAILS; the offline run must
NOT see `loaded` or it FAILS (offline is only proven offline if the remote
image demonstrably did not load, not just that a request was logged).
Falsified directly: pointing a scratch copy of the online fixture's `<img>`
at an unreachable address (`http://127.0.0.1:1/remote-image.png`)
reproduces `image_state:"failed"` and a PDF byte count identical to the
offline run (107,811 bytes) — the gate catches exactly the failure mode the
sleep could not, and this holds regardless of whether the image source is
local or remote, since the check gates on the in-page load event, not on
network behavior. In measured practice the image load now settles in
7–84ms (see Measurements below), so the fix also removed ~700ms of dead
waiting per run, not just the blind spot.

### Validation checks (`scripts/zs/pdf-validate.sh <pdf>`, the ticket's named
validator contract; both online and offline modes, exit 0)

- `pdfinfo` page count == 3 — PASS (both modes)
- `pdftotext -layout` contains all three headings (`Approval Page One`,
  `Materials Table`, `Approval ID Generator`) — PASS (both modes)
- `pdftotext -layout` contains **all four** table row tokens
  (`alpha-fixture-row`, `bravo-fixture-row`, `charlie-fixture-row`,
  `delta-fixture-row`), not just the first and last — PASS (both modes)
- `pdftotext -layout` contains the code block's **full comment line**
  (`# PDF_SPIKE_CODE_MARKER_7f3a`, not the bare token) — PASS (both modes)
- `pdftoppm -png` renders exactly 3 pages, `validate.sh` checks its exit
  code explicitly — PASS (both modes)
- **The rendered image is bound to the PDF's own image XObjects, not only
  the DOM's `load` event** (added in the Sol audit fix round —
  `image_state` alone proved the browser fired a JS event, not that
  anything ended up in the printed output: reproduced by setting
  `display:none` on the online fixture's `<img>`, which still reports
  `image_state=loaded` while the PDF drops to 105,374 bytes and
  `pdfimages -list` shows zero embedded images). `scripts/zs/pdf-validate.sh`
  now reads `pdfimages -list <pdf>`: online and negative-fixture PDFs must
  embed the reference image at its native 800×600 — PASS (both); the
  offline PDF must NOT embed a full-size image (only Chrome's small
  broken-image glyph, measured 14×16 here) and `pdftotext` must extract the
  image's alt text (`remote reference image`) — PASS. A PDF with the image
  silently stripped (no image at all) now fails this check regardless of
  what `image_state` reported.
- Online: renderer's `image_state` field (from the in-page `load`/`error`
  event promise, see above) is `loaded` — PASS. Falsified by construction:
  pointing a scratch copy of the fixture's `<img>` at an unreachable
  address reproduces `failed` and a 107,811-byte PDF (the offline size),
  proving the check actually gates rather than always passing. `validate.sh`
  also floors the online PDF at 300,000 bytes (measured well above the
  offline size) as a cheap independent signal that the reference image
  actually embedded.
- Offline: **the sentinel log must contain a well-formed `GET
  /remote-image.png?nonce=<run-nonce>` line, not merely be non-empty**
  (tightened in the Sol audit fix round — a bare TCP connect that sends no
  bytes was reproduced to satisfy the old non-empty check, and
  `sentinel.rs` now classifies every connection as `refused` (a real,
  parsed `GET`), `empty-request`, `malformed-request`, or `read-error`
  instead of discarding the read result, so only a genuine parsed request
  for this run's own nonce-bearing URL satisfies the check) — PASS, **and**
  the renderer's `image_state` field is exactly `failed`, not merely
  "not `loaded`" (also tightened — `missing`/`timeout` mean the
  instrumentation measured nothing, which the old check silently accepted)
  — PASS. `validate.sh`'s `run_offline_negative_control` step renders
  `fixtures/approval-offline-noinstrument.html` (byte-for-byte the offline
  fixture with only `class="remote"` removed from the `<img>`, so the
  browser still requests the image but the in-page selector can no longer
  find it) and requires `image_state=missing`, proving the tightened
  `failed`-exact check would correctly reject this broken-instrumentation
  case rather than passing it as before. The offline PDF's placeholder alt
  text is now asserted via `pdftotext` in `scripts/zs/pdf-validate.sh`
  itself (see the image-binding bullet above), so this is confirmed by
  script from `out/validate.log`, not only by visual inspection of a
  gitignored PNG.
- **Offline restricts one URL, not general egress — enforced, not only
  observed** (Sol audit finding 6): `validate.sh` now asserts
  `fixtures/approval.html`, `fixtures/approval-negative.html` and
  `fixtures/approval-offline-noinstrument.html` contain zero, zero and one
  external-reference pattern (`https?://`, `@font-face`, `<link>`,
  `<script>`, CSS `url()`) respectively, and `fixtures/approval-offline.html`
  contains exactly one (the sentinel `<img>`) — PASS (all four). A later
  fixture edit that adds any other external reference now fails this check
  instead of silently making "offline" mode not actually offline.

**Falsifiability of the row/code checks themselves.** Every prose paragraph
in the fixture originally repeated its own marker tokens verbatim to
"explain" them to a human reader — `alpha-fixture-row` through
`delta-fixture-row` in one sentence, `PDF_SPIKE_CODE_MARKER_7f3a` in
another. That made every token appear twice in the extracted text, so
deleting the table body or the code block entirely still left the checks
passing on the leftover prose occurrence — the checks were asserting the
tokens existed *somewhere in the document*, not that the structures they
claim to prove actually rendered. Fixed two ways: the prose now describes
each structure without repeating its literal token text (each token appears
exactly once, in its real structural location, in the current fixture), and
`scripts/pdf-spike/fixtures/approval-negative.html` — byte-for-byte
`approval.html` with only the four row tokens and the code marker line
replaced by unrelated text, page count unchanged at 3 — is rendered and
validated by `validate.sh`'s `run_negative` step as a required control: all
five affected checks must FAIL against it (they do — see
`scripts/pdf-spike/out/validate.log`), while every check on an untouched
structure (page count, all three headings) must still PASS (it does). A
check that cannot be made to fail this way is not proving anything; this
run proves all five now can be.

## Pick

Recommended, pending the owner sign-off above.

**Route (b), `headless_chrome` → Chrome's `Page.printToPDF`, for T9.** Route
(a) is not a contender: it cannot run unattended, has no bytes-out API on
this Tauri/wry pin, and its only headless alternative is barred by this
repo's no-`unsafe` rule. Route (b) is fully scriptable, produced a correct
3-page PDF with all structural content intact in both online and offline
runs, and degrades the remote image to a visible, non-silent placeholder
offline exactly as the ticket requires.

Costs T9 needs to account for, not resolved by this spike:

- **Chrome must be present on the machine.** This spike found it via
  `default_executable()`, which searches common install paths; `headless_chrome`
  also has a `fetch` feature that can download a pinned Chromium build, which
  T9 should evaluate for machines without Chrome installed (CI, some
  end-user machines) rather than assuming a system Chrome.
- **Cold-launch wall time (~3 s here) is a per-invocation Chrome process
  spawn**, not a lower bound on interactive latency; T9's e2e spec should
  measure a warm/reused-browser path if the feature is expected to feel
  instant from the viewer.
- **Every measurement above is fixture-relative** (deviation 1): sizes,
  timings, and page count describe this synthetic document, not
  `brand/render-approval.py`'s real output, and the fixture carries no
  brand font loading to fail on. Before T9 sets acceptance thresholds off
  these numbers, freeze a generated real approval-page HTML (waiting on
  `document.fonts.ready` before capture), hash it, and re-measure — with
  Devin's go-ahead, since it needs read access to the Broken English client
  project this worktree does not have.
- **Route (a) vs. route (b) pagination and font rendering is unmeasured**
  (deviation 3): the route pick does not depend on it, but a visual
  difference between what a person would get from the native print sheet
  and what T9 exports headlessly is not ruled out by this spike.

## Reproduce

Requires system `pdfinfo`/`pdftotext`/`pdftoppm`/`pdfimages` (poppler
26.07.0 on this machine) and a system Chrome (Google Chrome 152.0.7977.76
here, found via `headless_chrome::browser::default_executable()`) —
neither is vendored by the spike crate, so results on a different
poppler/Chrome build may vary slightly even though the checks above are
not expected to be sensitive to the exact version.

```
cd scripts/pdf-spike
./validate.sh           # always rebuilds via `cargo build --release --locked`,
                         # then: asserts each fixture's external-reference
                         # count; renders online + offline (starts/stops the
                         # sentinel, nonce-binding each offline run's
                         # sentinel-log evidence); renders the offline
                         # negative control (proves the tightened
                         # image_state=="failed" gate is falsifiable); renders
                         # the row/code-marker negative fixture; runs every
                         # check above, including the image-XObject binding
                         # check in scripts/zs/pdf-validate.sh
```

`scripts/zs/pdf-validate.sh <pdf>` (the ticket's named validator contract) can
also be run standalone against either rendered PDF, e.g.
`scripts/zs/pdf-validate.sh scripts/pdf-spike/out/approval-headless-chrome-online.pdf`.
