# PDF route decision (spike/pdf, ticket T8)

Date: 2026-09-04. Throwaway branch `spike/pdf`. No application code lands
from this branch — the harness that produced these numbers lives at
`scripts/pdf-spike/` for reproducibility and is not wired into the app; see
"Deviations from the ticket text" below for exactly what does land and why.

## Question

Render one document through (a) webview print-to-PDF behind a Tauri command
and (b) one Rust HTML-to-PDF crate. Pick a route for T9 (`feat/pdf-export`)
using measured numbers, not guesses.

## Route (a): webview print-to-PDF behind a Tauri command — not measurable, disqualified

This app pins `tauri = "2"` → `tauri 2.11.5` → `wry 0.55.1`
(`desktop/src-tauri/Cargo.lock`). Tauri's `WebviewWindow::print()` forwards to
`wry`'s webview `print()` on desktop. Quoted in full below, not excerpted —
read directly from the pinned `wry` source
(`~/.cargo/registry/src/.../wry-0.55.1/src/wkwebview/mod.rs:858-898`, macOS
backend):

```rust
pub fn print(&self) -> crate::Result<()> {
  self.print_with_options(&PrintOptions::default())
}

pub fn print_with_options(&self, _options: &PrintOptions) -> crate::Result<()> {
  // Safety: objc runtime calls are unsafe
  #[cfg(target_os = "macos")]
  unsafe {
    // <https://developer.apple.com/documentation/webkit/wkwebview/printoperation(with:)>
    // Available: macOS 11+
    let can_print = self
      .webview
      .respondsToSelector(objc2::sel!(printOperationWithPrintInfo:));
    if can_print {
      // Create a shared print info
      let print_info = objc2_app_kit::NSPrintInfo::sharedPrintInfo();
      print_info.setTopMargin(_options.margins.top.into());
      print_info.setRightMargin(_options.margins.right.into());
      print_info.setBottomMargin(_options.margins.bottom.into());
      print_info.setLeftMargin(_options.margins.left.into());

      // Create new print operation from the webview content
      let print_operation = self.webview.printOperationWithPrintInfo(&print_info);

      // Allow the modal to detach from the current thread and be non-blocker
      print_operation.setCanSpawnSeparateThread(true);

      // Launch the modal
      let window = self.webview.window().unwrap();
      print_operation.runOperationModalForWindow_delegate_didRunSelector_contextInfo(
        &window, None, None, std::ptr::null_mut(),
      )
    }
  }

  Ok(())
}
```

The `respondsToSelector` guard and the four margin setters were omitted from
this section's code block in an earlier draft; both are quoted here. The
guard does not change the conclusion below — when it is `false` the function
silently produces no output at all, which is a stricter failure than the
modal path, not an escape from it. `PrintOptions` (same file, line 127-129):

```rust
#[derive(Debug, Default, Clone)]
pub struct PrintOptions {
  pub margins: PrintMargin,
}
```

Three facts fall out of this, not from speculation:

1. **It is modal, not headless.** `runOperationModalForWindow_delegate_...`
   attaches an `NSPrintOperation` to a real, visible `NSWindow` and runs it as
   an application-modal sheet. There is no way to invoke it without a window
   on screen, and it returns to the caller once the modal is *dismissed* by
   a person (approving or canceling), not once a file exists.
2. **There is no bytes/file output path.** `PrintOptions` carries only print
   margins. Unlike Electron's `webContents.printToPDF()` or Chrome DevTools'
   `Page.printToPDF`, wry's wrapper does not expose a "print silently to a
   buffer" mode — the only supported outcome is the OS print panel, from
   which a human chooses "Save as PDF" themselves.
3. **The only way around (1) and (2) is to bypass wry and call
   `WKWebView.createPDF(configuration:completionHandler:)` directly**, which
   requires the same class of `unsafe` Objective-C interop wry uses
   internally. This repository's hard rule (`AGENTS.md` "Quality Gates": *no
   `unsafe` code*) forbids adding that in application code.

Given (1)-(3), route (a) cannot produce a PDF through a script — every
export requires a human to click through a native print sheet — so it has no
number to report for the pdftotext/pdftoppm/size/wall-time checks below. This
alone is disqualifying for an export feature (T9) that needs to run
unattended from a menu action and be exercised by an e2e spec. No live Tauri
command was built to reconfirm this: the pinned dependency source already
settles it conclusively, and standing up a windowed app in this environment
to re-derive the same fact from the same code path was not a good use of a
half-day spike budget.

## Route (b): Rust HTML-to-PDF crate — `headless_chrome` 1.0.22

`headless_chrome` (MIT, `scripts/pdf-spike` — a standalone Cargo project, not
a workspace member) drives a local Chrome/Chromium binary over the DevTools
Protocol and
calls `Page.printToPDF`, which *is* a headless, non-interactive, bytes-out
API — the thing route (a) is missing. Harness:
`scripts/pdf-spike/src/render_headless_chrome.rs`. It found Chrome via
`headless_chrome::browser::default_executable()` (`/Applications/Google
Chrome.app` on this machine — a real, separately-installed browser, not
bundled with the crate).

Offline mode is not a Chrome-launch flag any more — an earlier draft of this
harness used `--proxy-server=127.0.0.1:1` (an unreachable local port) to
black-hole every outbound request, but that only produces a broken-image
placeholder and a byte-count drop, both of which are equally consistent with
the image request never having been issued at all as with it being issued
and failing. Neither is a measurement of an attempt.

Instead, per the ticket text, the offline fixture's remote `<img>` points at
a local sentinel HTTP server (`scripts/pdf-spike/src/sentinel.rs`, a second
binary in the same throwaway crate) bound to `127.0.0.1:18391`. The sentinel
accepts every TCP connection, logs the peer address and request line to a
file, and refuses the request with `403 Forbidden` before closing the
connection — it never serves the image. `validate.sh` starts the sentinel,
waits for its readiness line on stdout, runs the offline render against
`fixtures/approval-offline.html`, then asserts the sentinel's log file is
non-empty before tearing it down. This is a measurement, not an inference:
the log line

```
1788514280113 refused peer=127.0.0.1:56230 request=GET /remote-image.png HTTP/1.1
```

is direct proof the renderer issued the request and the sentinel received
it, independent of anything the resulting PDF looks like. No firewall rules
are changed, matching the ticket's constraint.

The online side needs the mirror-image proof: not just that the fetch was
attempted, but that it actually *succeeded* before the page was captured. An
earlier version of this harness synchronized on a flat `std::thread::sleep`
before printing — 800ms, chosen by feel, undisclosed inside the reported
wall time. That is not a check: if the Wikimedia fetch had taken longer than
800ms or failed outright, the harness would still print whatever was on the
page at that instant and every downstream validator check (page count,
headings, table cells, code marker, PNG render) would still pass, because
none of them look at the image. The harness now awaits the fixture's
`<img class="remote">` element directly, in-page, via a
`load`/`error`-event `Promise` (`wait_for_remote_image` in
`render_headless_chrome.rs`), bounded by a 5s in-page timeout, and reports
the settled state — `loaded`, `failed`, `timeout`, or `missing` — as
`image_state` in the JSON line, timed separately (`image_wait_ms`) from the
print itself (`print_ms`). `validate.sh` asserts on that field: the online
run must see `image_state=loaded` or the run FAILS; the offline run must
NOT see `loaded` or it FAILS (offline is only proven offline if the remote
image demonstrably did not load, not just that a request was logged).
Falsified directly: pointing the online fixture's `<img>` at an
unreachable address reproduces `image_state:"failed"` and a PDF byte count
identical to the offline run (110,006 bytes) — the gate catches exactly the
failure mode the sleep could not. In measured practice the image now
settles in 10–155ms (see Measurements below), so the fix also removed
~700ms of dead waiting per run, not just the blind spot.

### Measurements

Five independent runs (fixture is deterministic; wall time includes cold
Chrome launch each run, not warmed up), plus a sixth committed run through
`validate.sh` itself. Validated by `scripts/pdf-spike/validate.sh` (which
delegates per-PDF structural checks to `scripts/zs/pdf-validate.sh <pdf>`,
the validator contract named in the ticket text, and asserts `image_state`
per mode as described above); full output of the committed run is in
`scripts/pdf-spike/out/validate.log`.

The 4.5x size drop between modes is the remote image: present and embedded
online, absent offline. Byte count and wall-time order-of-magnitude are
stable run-to-run; **the PDF's own sha256 is not** — it differed on every run
while the byte count did not. Root cause, not yet chased further:
Chrome's `Page.printToPDF` embeds a `/CreationDate`-style timestamp in the
PDF container, so two structurally identical PDFs hash differently. The
rendered *content* is confirmed identical across runs by the `pdftoppm` PNG

this fix round, and are byte-for-byte the same hash values already recorded
on this branch from the pre-image-gate (flat-sleep) harness version this
round replaced — the visual output is unchanged; only the proof mechanism
and the wasted wait time are. T9's own "hash of
the output for the fixture
recorded in the PR" acceptance check should hash the extracted content (or a
PNG render) rather than the raw PDF bytes, or it will flake on every re-run
for a reason that has nothing to do with correctness.

### Validation checks (both modes; `validate.sh`, exit 0)

- `pdfinfo` page count == 3 — PASS (both modes)
- `pdftotext -layout` contains all three headings (`Approval Page One`,
  `Materials Table`, `Approval ID Generator`) — PASS (both modes)
- `pdftotext -layout` contains the table's distinguishing cell tokens
  (`alpha-fixture-row` … `delta-fixture-row`) — PASS (both modes)
- `pdftotext -layout` contains the code block's marker line
  (`PDF_SPIKE_CODE_MARKER_7f3a`) — PASS (both modes)
- `pdftoppm -png` renders exactly 3 pages, `validate.sh` checks its exit
  code explicitly — PASS (both modes)
- Online: renderer's `image_state` field (from the in-page `load`/`error`
  event promise, see above) is `loaded` — PASS. Falsified by construction:
  pointing the fixture at an unreachable address reproduces `failed` and
  a 110,006-byte PDF (the offline size), proving the check actually gates
  rather than always passing.
- Offline: sentinel log file is non-empty after the render (measured, see
  above) — PASS, **and** the renderer's `image_state` field is not
  `loaded` (measured `failed`) — PASS. Remote image renders as a visible
  broken-image placeholder
  with its alt text (`remote reference image`) shown inline, not a blank
  rectangle — confirmed visually from `out/png-offline/page-1.png`, PASS.

## Pick

**Route (b), `headless_chrome` → Chrome's `Page.printToPDF`, for T9.** Route
(a) is not a contender: it cannot run unattended, has no bytes-out API on
this Tauri/wry pin, and its only headless alternative is barred by this
repo's no-`unsafe` rule. Route (b) is fully scriptable, produced a correct
3-page PDF with all structural content intact in both online and offline
runs, and degrades the remote image to a visible, non-silent placeholder
offline exactly as the ticket requires.

Two costs T9 needs to account for, not resolved by this spike:

- **Chrome must be present on the machine.** This spike found it via
  `default_executable()`, which searches common install paths; `headless_chrome`
  also has a `fetch` feature that can download a pinned Chromium build, which
  T9 should evaluate for machines without Chrome installed (CI, some
  end-user machines) rather than assuming a system Chrome.
- **Cold-launch wall time (~3 s here) is a per-invocation Chrome process
  spawn**, not a lower bound on interactive latency; T9's e2e spec should
  measure a warm/reused-browser path if the feature is expected to feel
  instant from the viewer.

## Reproduce

Requires system `pdfinfo`/`pdftotext`/`pdftoppm` (poppler 26.07.0 on this
machine) and a system Chrome (Google Chrome 152.0.7977.76 here, found via
`headless_chrome::browser::default_executable()`) — neither is vendored by
the spike crate, so results on a different poppler/Chrome build may vary
slightly even though the checks above are not expected to be sensitive to
the exact version.

```
cd scripts/pdf-spike
cargo build --release
./validate.sh          # renders online + offline (starts/stops the sentinel),
                        # runs every check above, including the sentinel-log
                        # and image_state assertions
```

`scripts/zs/pdf-validate.sh <pdf>` (the ticket's named validator contract) can
also be run standalone against either rendered PDF, e.g.
`scripts/zs/pdf-validate.sh scripts/pdf-spike/out/approval-headless-chrome-online.pdf`.
