Approval Page One — Vendor Onboarding

This fixture stands in for the Broken English approval-page generator (brand/render-approval.py), which lives in a separate client project not reachable from this worktree. It is a synthetic document built to exercise the same shapes a real approval page needs validated: a heading structure, a data table, a code block, a remote image, and enough running text to span three printed pages at US Letter with 0.75in margins.

Filler paragraph 1. The quick brown fox jumps over the lazy dog near the riverbank while the autumn light fades across the workshop floor. Every vendor approval cycle begins with a short intake form, a signature block, and a checklist of the materials the studio expects back before the piece moves into production scheduling.

Filler paragraph 2. Reviewers read the brief twice: once for the stone specification and once for the metal alloy and plating notes. A third pass checks the delivery window against the studio's current backlog, since late vendor turnaround is the single largest cause of missed launch dates across the last four collections.

Filler paragraph 3. The approval record itself is short, but the context around it is not: photography references, prior revision notes, and a running thread of email correspondence all attach to the same record so that anyone opening it six months later can reconstruct why a decision was made and who made it.

Filler paragraph 4. When network access is unavailable, this image must degrade to a visible placeholder or a cached copy rather than silently producing a blank rectangle indistinguishable from a broken layout, because a vendor approval page is a compliance artifact and a missing image should never look like a rendering bug.

Filler paragraph 6. Between the table and the code block sits the section of the brief that explains how the approval id is generated: a short deterministic function keyed off the vendor code, the collection season, and a monotonic counter, so that two approvals issued the same day never collide even when generated by different reviewers working offline.

Approval ID Generator

def approval_id(vendor_code: str, season: str, counter: int) -> str:
    # deterministic id, no external state
    return f"{vendor_code.upper()}-{season}-{counter:04d}"

Filler paragraph 7. The comment on the second line of the code block above is the line an automated extraction check looks for. Its exact text is defined once, inside the code block itself, and is deliberately not repeated anywhere else on this page, so finding it in extracted text is proof the code block rendered rather than proof the phrase merely occurs somewhere.

Filler paragraph 8. The remainder of this page is running text whose only job is to push the document to a third printed page without changing any of the structural elements already covered above. Word count, not meaning, is what matters from here down.

Filler paragraph 9. Vendor relationships at this scale are managed through a small number of long-running threads rather than one-off tickets, and the approval record is the anchor every later message in that thread refers back to, which is why its rendering fidelity — headings, tables, code, and images all surviving a headless export — is worth spiking before committing to one PDF route over another.

Filler paragraph 10. This paragraph, and the ones immediately following, exist purely as layout ballast: measured filler whose length was tuned against this exact print stylesheet so the fixture lands on three pages, not two and not four, when rendered through either PDF route under test.

Filler paragraph 11. Ballast continues. The workshop's Tuesday intake window closes at noon; anything arriving after that rolls to the following week's queue automatically, and the queue position is recorded on the approval record itself so a vendor can see where they stand without opening a separate ticket.

Filler paragraph 12. Ballast continues. Historically, the studio found that approval pages reviewed on a phone screen were approved 30% faster than the same page reviewed on a laptop, which is a minor detail but one reason the print layout is kept deliberately narrow and linear rather than using a multi-column layout that would need horizontal scrolling on a small screen.

Filler paragraph 13. Ballast continues. The last paragraph on this page restates the point of the whole fixture: it is not a real vendor document, it is a stand-in shaped like one, built so the PDF route decision in this spike rests on numbers measured against a fixed, hashed input rather than on an ad hoc test page assembled differently for each route.
